## 1. PHASE 0 - 캡처 루프가 VideoFrame 입력으로 바뀌어도 유지되는가 (코드 읽기)

현재 송출 흐름 **[코드]**:

```
getUserMedia/getDisplayMedia -> <video> -> Worker 타이머 틱(/capture-timer.js, intervalMs=1000/recommendedFps)
  -> drawFrameToCanvas()  (가로 1280 제한, 90도 단위 회전을 캔버스에서 처리)
  -> canvas.toBlob('image/jpeg', 0.8) -> 최신 1장만 큐 -> POST /api/streams/v1/stream-sessions/{id}/frame (동시 2건, 429 휴지)
```

| 기존 동작 | VideoFrame 입력으로 바꿨을 때 | 판정 |
|---|---|---|
| Worker 타이머(탭이 숨겨져도 fps 유지) | 타이머는 그대로 두고 `toBlob` 자리만 `new VideoFrame(canvas, {timestamp})` -> `encoder.encode()`로 교체. 타이머·캔버스 경로를 건드리지 않는다 | **유지** |
| 회전(0/90/180/270) | 회전이 이미 캔버스에서 끝나므로 인코더는 회전된 캔버스만 본다. 단 90/270으로 바꾸면 캔버스 가로·세로가 뒤바뀌어 **인코더 재설정(configure) + 키프레임**이 필요 | **유지(재설정 처리 추가)** |
| 화면 공유(`getDisplayMedia`) | 같은 캔버스 경로라 동일. 공유 창 크기가 바뀌면 해상도가 변하므로 회전과 같은 재설정 경로를 탄다. 화면 공유는 지금 **시연용으로 선택지가 숨겨진 상태**(`?screen=1`)라 PoC 합격 기준에서 제외 가능 | **유지(재설정)** |
| 해상도 1280 제한 | 그대로 적용. 단 H.264는 **가로·세로가 짝수여야** 하므로 `Math.round` 결과를 짝수로 맞추는 한 줄이 필요 | **유지(짝수화 추가)** |
| 최신 프레임만 보내기(밀리면 버림) | JPEG는 프레임이 독립이라 버려도 무해하지만 **H.264는 P프레임을 버리면 이후 프레임이 깨진다**. 큐에서 버리는 대신 `encoder.encodeQueueSize`가 임계(예: 2)를 넘으면 **인코더 입력 단계에서 건너뛰고**, 전송 버퍼(WS `bufferedAmount`)가 밀리면 **다음 키프레임까지 버린다** | **정책 변경 필요** |
| 429 휴지·`MAX_IN_FLIGHT` 2·`resetUploadHealth` | HTTP 요청 단위 개념이라 WS에는 그대로 맞지 않는다. WS 한 줄 연결이라 429가 사라지고 대신 "연결 끊김 -> 재연결(새 자격)"이 불안정 판정의 기준이 된다. `UNSTABLE_FAIL_*` 판정은 `onclose`·전송 지연으로 대체 | **대체** |
| 프록시의 프레임마다 로그인 확인(PR #35 캐시) | WS는 **연결 수립 시 1회** 자격 확인이라 이 부담이 사라진다(이번 송출 끊김의 근본 원인이 구조적으로 해소) | **개선** |
| 모달을 닫아도 송출 유지, 언마운트에서 stop 호출 안 함 | 인코더·WS를 ref로 들고 있어야 하므로 기존 `captureWorkerRef`와 같은 방식으로 보관. 언마운트 정리에서 **인코더 close·WS close**를 추가(stop 호출 여부는 기존 결정 유지) | **유지(정리 추가)** |
| wake lock·`visibilitychange` | 영향 없음 | **유지** |
| 미리보기(`startPreviewLoop`) | 영향 없음 | **유지** |

**결론**: 캡처·회전·화면 공유·타이머는 `toBlob`을 `VideoFrame`+`encode`로 바꾸는 것만으로 유지된다. **MediaStreamTrackProcessor를 쓰지 않는 것이 핵심**이다(Chromium 계열만 지원 **[문서]**이고, 쓰면 캔버스 회전·1280 제한 경로를 버려야 한다). 바뀌는 것은 "프레임 단위 독립 전송"이라는 전제 하나다(키프레임 의존).

4. WS 연결·자격 발급 실패, 인코더 `error` 콜백, 첫 키프레임 전송 실패 -> **그 세션은 JPEG로 되돌린다**(되돌린 뒤 같은 세션에서 H.264로 다시 올라가지 않음 - 플래핑 방지)

## 4. 업로드 WS 연결 위치 (BE·AI 설계와 맞출 안)

### 4-1. 후보

| 후보 | 경로 | FE 의견 |
|---|---|---|
| **P1 (권장 제안)** | 브라우저 -> `wss://api.devdmu.gosky.kr/ws/...`(BE) -> AI. BE가 일회용 업로드 자격으로 핸드셰이크를 인가하고 프레임을 AI에 중계 | FE는 이미 `wss://api.devdmu.gosky.kr/ws`(STOMP)를 쓰고 있어 **업그레이드·CORS·Origin 경로가 검증된 도메인**이다 **[코드: `connectionSocket.ts`]**. AI 키가 서버 안에 머문다. 단 BE가 프레임을 중계하므로 BE 스레드·메모리 부하가 생긴다(BE 설계 3-1 "프레임 단위 중계" 항목) |
| P2 | 브라우저 -> `wss://<AI 도메인>/...` 직결, BE 발급 일회용 자격 | BE 부하가 없지만 AI 서버가 자격 검증기를 새로 갖춰야 하고 AI 도메인 nginx가 WS를 통과시키는지 확인이 필요(기존 AI WS는 백엔드가 헤더 키로 붙던 것). 키 대신 자격만 쓰는 구조가 되려면 AI 개발이 큼 |
| P3 | Next 서버(`devdmu.gosky.kr`)에서 WS 중계 | route handler로 불가. 커스텀 서버가 필요해 `next dev` 컨테이너 구성을 바꿔야 하므로 **권장하지 않음** |

### 4-2. FE 쪽 가정과 요구사항 (BE·AI에 전달할 항목)

- 자격 발급: `POST /api/ward/camera/{cameraId}/...`류 REST(이름은 BE 몫)로 **1회용·세션 바인딩·60초** 자격을 받고, WS URL의 쿼리 `?ticket=`로 붙는다. **access 토큰을 쿼리에 싣지 않는다**(BE 규칙과 동일). 자격은 피보호자 본인 카메라 한정(시청 자격과 분리, BE 설계 3-3).
- 연결 중 갱신·종료: BE가 60초 재확인으로 끊으면 `1008`/`AUTH_INVALIDATED` 같은 close 코드를 준다고 가정 -> FE는 **재연결하지 않고** 자격을 다시 받아 한 번만 재시도, 실패하면 JPEG 폴백 또는 중단 안내.
- 메시지 계약(FE 제안, AI와 확정 필요 **[미정]**): 첫 텍스트 메시지 `{type:'config', codec, width, height, framerate, format:'annexb'}`, 이후 바이너리 1프레임=1메시지 `[8바이트 타임스탬프(us)][1바이트 플래그: 키프레임][H.264 Annex B 데이터]`. 해상도·회전 변경 시 새 `config` 후 키프레임. 서버는 필요 시 `{type:'keyframe_request'}`를 보낼 수 있어야 한다(디코더 복구용).
- nginx: `api.devdmu.gosky.kr`의 **새 경로가 `Upgrade`/`Connection` 헤더를 통과시키는지**, 바이너리 메시지 크기·`proxy_read_timeout`(무프레임 구간)이 충분한지는 인프라 관리 밖이라 **확인 필요 [미정]**. 기존 `/ws`가 되므로 같은 location 규칙 아래 두면 새 설정이 필요 없을 가능성이 높다 **[추정]**.
- 송출 종료: 지금처럼 `POST .../stop`(프록시 경유)을 유지하는 것을 제안(세션 종료는 기존 AI 경로 그대로, WS close만으로 종료를 판정하지 않음).

## 5. 일 단위 견적 (FE 몫만, 1인 기준, 테스트·문서 포함)

| 항목 | A. WebRTC | B. WS + WebCodecs |
|---|---|---|
| 지원 검사·폴백 분기(코드 경로 분리) | 1 | 1 |
| 캡처 -> 인코더/PeerConnection 연결, 회전·화면 공유 재설정 | 2~3 | 2 |
| 전송(WS 프레이밍 / 시그널링·ICE) | 3~4 (시그널링 서버·STUN/TURN 설정 협의 포함) | 1.5 |
| 재연결·자격 재발급·불안정 안내(기존 `isUnstable` UI 재사용) | 1.5 | 1.5 |
| 단위 테스트(분기·재설정·폴백) + 실기기 확인 | 2 | 2 |
| **합계** | **약 9.5~11.5일** | **약 8일** |

- 전제: BE 자격 API와 AI 수신부 계약이 **확정돼 있을 때**의 FE 몫이다. 계약이 확정되기 전 PoC는 로컬 에코 서버로 인코더 동작만 검증할 수 있다(약 1.5일, 합계에 미포함).
- A가 큰 이유는 시그널링(SDP·ICE) 처리와 NAT 환경 시험이다. 가정 네트워크의 TURN 필요 여부는 **FE만으로 단정할 수 없고** 인프라 협의가 필요하다. 요청서 5-5에 대한 FE 의견: **B를 먼저 PoC**한다(구조가 현재 서버와 가깝고 STUN/TURN이 없다). A는 B의 한계가 확인된 뒤.
- 불확실도: 실기기 지원 범위(특히 iPad Safari)에 따라 폴백 비중이 커지면 이득 구간이 줄어든다. **"전환 후 체감 개선"은 아직 확인된 것이 없다**(요청서도 감지 정확도 향상 보장 없음이라고 명시).

## 6. PHASE 1 - 설계안

### 6-1. 폴백 규칙 (코드 경로 분리, 기존 동작 보존)

```
송출 시작 시 1회 판정(모듈 함수 selectTransport):
  server.transport === 'h264-ws'  AND  VideoEncoder 지원  AND  isConfigSupported  AND  자격 발급 성공  ->  'h264'
  그 밖 전부  ->  'jpeg'  (현재 코드 그대로)

jpeg 경로: startCaptureLoop 의 toBlob -> enqueueLatestFrame -> uploadFrame (지금 코드에서 한 줄도 바꾸지 않는다)
h264 경로: 새 모듈(예: lib/stream/h264Sender.ts)이 캔버스 -> VideoFrame -> VideoEncoder -> WS 를 담당
```

- 분기 지점은 `startCaptureLoop`의 Worker `onmessage` 한 곳(`toBlob` 대신 `sender.push(canvas)`). 나머지(등록·sessionId·미리보기·wake lock)는 건드리지 않는다.
- 새 방식은 **PoC 플래그**(예: `NEXT_PUBLIC_VIDEO_TRANSPORT_POC=1` 또는 `?transport=h264`)가 켜지고 서버도 허용할 때만 시도한다. 플래그가 없으면 어떤 환경에서도 지금과 동일하게 동작한다.
- 런타임 실패(인코더 error, WS 비정상 종료 2회, 키프레임 이후 30초 무응답 등)면 같은 세션을 JPEG로 되돌린다. 이 전환은 사용자에게 문구 없이 하고 `console` 대신 서버 로그가 아닌 **이벤트 카운터만**(영상·토큰·쿠키 원문 로그 금지).

### 6-2. 인코더 설정과 근거

| 항목 | 값 | 근거 |
|---|---|---|
| codec | `avc1.42E01F`(Baseline 3.1) 우선, 미지원이면 `avc1.4D401F`(Main) | 폰 하드웨어 인코더 호환이 가장 넓음. 서버 디코더(ffmpeg/PyAV)에서도 안전 |
| 해상도 | 현재 규칙 유지: 가로 최대 1280, 짝수화. 720p급 | 감지 모델 입력과 현재 JPEG 해상도를 맞춰 **비교 변수를 줄인다**(변수는 압축 방식 하나만) |
| framerate | 서버가 준 `recommendedFps`(현재 10, 시험은 15) | 현재 로직과 동일. 인코더 `framerate`는 비트레이트 배분용 힌트 |
| bitrate | 720p 15fps 기준 **1.5Mbps**(범위 1.0~2.0), 화면 공유는 2.5Mbps | 실시간 H.264 720p의 일반 구간 **[문서]**. 감지(작은 연기·불꽃) 보존을 위해 1.0 미만으로 낮추지 않는다 |
| bitrateMode | `variable`(미지원이면 기본값) | 움직임이 적으면 줄고 화재 같은 변화에 여유 |
| latencyMode | `realtime` | B-프레임 금지·지연 최소 |
| avc.format | `annexb` | 프레임 한 건이 SPS/PPS를 포함해 서버가 중간 합류·복구하기 쉽다 |
| 키프레임 간격 | **2초**(fps x 2프레임마다 `keyFrame:true`) + 첫 프레임 + 재설정 직후 + 서버 요청 시 | 길면 유실 복구가 느리고, 짧으면 전송량이 는다. 2초는 클립 앞 구간(3~8초)·시청 합류 지연의 타협 |
| hardwareAcceleration | `no-preference` | 기기가 알아서. 강제 시 미지원 기기가 늘어남 |
| 큐 상한 | `encodeQueueSize > 2`이면 새 프레임 건너뜀 | 지연 누적 방지(현재 "최신 1장만" 정책의 H.264판) |

### 6-3. 15fps 기준 전송량 예상 (추정, 실측 아님)

| 방식 | 프레임·비트레이트 | 초당 | 분당 |
|---|---|---|---|
| 현재 JPEG q0.8 | 66KB(10/13 실측 평균) x 15 = 약 1.0MB/s, BE 10/14 재측정 프레임 0.1MB 안팎이면 약 1.5MB/s | **약 8~12Mbps** | 약 60~90MB |
| H.264 1.5Mbps | 고정 | **약 1.5Mbps** (키프레임 포함 평균, 순간 상한 2배) | 약 11MB |

- 예상 절감 **약 5~8배**(추정). 가정 인터넷 업로드 대역폭은 현재도 병목이 아니라고 요청서가 밝히고 있어, 이득은 **전송량보다 끊김·지연 안정성**에서 나오는지 확인하는 것이 PoC의 목적이다.
- 서버 측 부담 이동: JPEG는 디코딩이 필요 없었지만 H.264는 AI 서버가 디코딩해야 하므로 **AI 분석 스레드 여유(3대 15fps에서 86%)가 줄 수 있다** -> 측정 항목에 포함.

### 6-4. 위험과 점검 항목

- **감지 품질**: AI의 화면 품질 게이트·시간 기준 유지 조건(최근 2초 중 60% 양성)은 JPEG 프레임 특성을 가정해 만들어졌다. H.264 아티팩트(블록·번짐)가 게이트 판정과 화재 신뢰도를 바꿀 수 있어 **감지 일치 비교가 필수**다(7절).
- **키프레임 의존**: 패킷 유실 없는 TCP(WS)이므로 유실은 드물지만, FE가 큐에서 버린 프레임은 디코더를 깨뜨린다 -> 6-2의 "입력 단계 스킵"이 핵심.
- **분석 지연 구간**: 인코더 큐 + WS + 서버 디코드가 더해져 화재 알림 시각이 늦어질 수 있다 -> 7절에서 **프레임 캡처 시각 대비 AI 분석 시각**을 비교.
- **iPad 가능성**: 폴백이 JPEG라 영향은 "이득이 없음"이지 "송출 실패"가 아니도록 기능 검사로만 분기한다.

## 7. 테스트 방법 (1대, 같은 장면)

전제: BE 자격 API와 AI 수신부가 갖춰진 **구현 이후**의 실측. 이전에는 로컬 에코 서버로 인코더·분기만 확인한다.

1. 장면 고정: 같은 방·조명에서 **같은 입력을 두 방식에 동일하게** 주기 위해, 화면 공유 모드로 **재생 영상 파일**(정상 장면 + 불꽃/연기 시연 구간)을 쓰거나, 카메라를 고정하고 JPEG 5분 -> H.264 5분 순으로 같은 장면을 반복한다. 순서 효과를 줄이려 JPEG -> H.264 -> JPEG 3구간으로 한다.
2. 측정 항목(구간마다 같은 기준):

| 항목 | 방법 | 비교 기준 |
|---|---|---|
| 전송량 | 브라우저 Network·WS 합계 바이트 / 구간 길이 | JPEG 대비 비율 |
| 최대 프레임 간격 | AI `status`·`latest-frame` 읽기 전용 폴링(BE 측정과 같은 방식, 도착 시각 기록) | 1초 이상 간격 횟수 |
| 평균·중앙 fps | AI 보고 fps | `recommendedFps`와의 차이 |
| 감지 일치 | 같은 장면 구간의 AI 판정(`danger`·type·confidence)을 이력 행으로 비교 | 구간 단위 일치율, 불일치 시 confidence 차이 |
| 감지 지연 | 시연 이벤트 시각 -> `anomaly_event` 적재 시각 | JPEG 대비 증감 |
| 서버 부하 | AI 프레임당 처리 시간·분석 사용률 | 디코드 추가분 |
| 클립 | 낙상·화재 클립의 길이·프레임 수 | 앞 구간 단축 여부 |

3. 합격 기준(제안, 승인 시 확정): ① 전송량 JPEG의 50% 이하 ② 최대 프레임 간격이 JPEG보다 나쁘지 않을 것 ③ 시연 위험 구간 **감지 누락 0건**(일치율 100%) ④ 폴백 강제(플래그 off·미지원 흉내) 시 기존 동작 동일 ⑤ 회전·화면 공유 전환 후 영상이 깨지지 않음.
4. 로그 규칙: 토큰·쿠키·영상 원문을 로그·문서에 남기지 않는다. 측정은 바이트 수·시각·판정 값만 기록한다.

## 8. 승인 요청 / 결정 필요

1. **B안(WS + WebCodecs)을 PoC 대상으로** 진행하는지(요청서 5-5 FE 의견: B 먼저, A는 B의 한계 확인 후).
2. 업로드 WS 위치 **P1(BE 중계)** 제안에 동의하는지. BE·AI 세션에서 자격 API·메시지 계약을 확정해야 FE가 착수할 수 있다.
3. 요청서가 제안한 순서(C 먼저)와의 관계: 송출 끊김 수정(PR #35) 뒤 **fps 15 재시험(C)** 결과가 나오기 전에는 PoC 착수를 보류하는 것을 권장.
4. 실기기 확인 대상 목록(폰 모델·삼성 인터넷/Chrome 버전·iPad 사용 여부) 제공: 2절 지원 표를 실측으로 바꾸는 데 필요하다.

> 이 문서는 설계이며 코드·배포 변경이 없다. 승인 후 구현은 AI·BE 구현이 끝난 뒤 마지막에 진행한다.
