# 송출 끊김 수정 - 프록시 로그인 확인 캐시, 429/401 구분, 실패 안내 (2026-10-14)

## 배경
- `/api/streams/[...path]` 프록시가 프레임 업로드마다 백엔드 `/api/user/me`로 로그인·역할을 확인했다.
  송출 중 요청이 초당 10건 이상이라 백엔드 속도 제한(429)에 걸렸고, 프록시는 실패를 모두 401로 바꿔 돌려줬다.
- 클라이언트는 업로드 실패를 `.catch(() => {})`로 삼켜 사용자도, 코드도 끊긴 것을 알 수 없었다.

## 변경
- `src/lib/server/wardAuth.ts`: 로그인 확인 결과 캐시. 성공(WARD)만 30초, 키는 토큰 SHA-256, 최대 500개,
  같은 토큰의 동시 확인은 한 번만 호출. 401·429·5xx·다른 역할은 캐시하지 않는다.
- 프록시: 확인이 429면 429(+`Retry-After`), 401/403은 401, 다른 역할은 403, 일시 장애는 503.
- `streamClient`: 401이면 토큰 재발급 1회 후 같은 요청 재시도. 429는 재시도하지 않는다.
- `CameraRegisterModal`: 429면 `Retry-After`만큼 업로드를 쉰다. 연속 5회 또는 3초 실패 시 안내, 성공하면 해제.
  "다시 켜기" 성공 직후 상태 조회를 즉시 갱신한다.
- `WardCameraContent`: 상태 조회가 실패해 목록이 비면 "연결 상태 확인 중" 안내를 보여 준다(등록 버튼이 사라지던 문제).

## 바뀌지 않는 것
송출 fps 로직·캡처 Worker·회전·화면 공유·sessionId·등록 흐름, 모달 닫기 시 송출 유지(언마운트 stop 호출 안 함).

## 수동 확인 (gosky 배포 후, 3분 이상 송출)
1. 피보호자 계정으로 카메라 송출 시작.
2. 브라우저 개발자 도구 Network에서 `/api/streams/v1/stream-sessions/*/frame`의 401·429가 0건인지 확인.
3. 서버에서 `/api/user/me` 호출이 송출 중 분당 한 자릿수인지 확인(프록시 → 백엔드 접근 로그).
4. 송출 시작 후 15초 안에 보호자 화면 "연결됨"이 나타나고 유지되는지 확인.
5. 네트워크를 잠시 끊었다 켜서 안내 문구가 나타나고 복구 시 사라지는지 확인.
